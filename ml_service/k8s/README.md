# Платформа в Kubernetes

Манифесты для переноса «Монетки» из Docker Compose в кластер. Это учебный
перенос ядра, а не полный стек: здесь ровно те объекты, на которых видно
разницу между Compose и Kubernetes. Что осталось в Compose и почему — в конце.

Теория — в [`docs/kubernetes-course.md`](../docs/kubernetes-course.md).

---

## Что поднимается

| Объект | Тип | Почему именно такой |
|:---|:---|:---|
| `postgres` | StatefulSet + headless Service + PVC | База. Под №1 не равен поду №2 |
| `monetka-api` | Deployment + Service | Без состояния, но том RWO держит одну реплику |
| `monetka-data`, `monetka-artifacts` | PVC | Склад DuckDB — один файл, один писатель |
| `monetka-config` | ConfigMap | Настройки |
| `monetka-secrets` | Secret | Доступы, отдельно от настроек |

## Если кластер не создаётся: сначала проверьте cgroup

На это ушло три неудачные попытки, поэтому вынесено наверх.

В WSL2 кластер падал с `exit status 137`, и это выглядело как нехватка памяти —
тем более что машина восьмигиговая. Памяти хватало. Настоящая причина нашлась в
логах k3s:

```
failed to validate kubelet configuration, error: kubelet is configured to not
run on a host using cgroup v1
```

**WSL монтирует контроллеры cgroup v1 рядом с v2** — гибридный режим, на котором
современный kubelet запускаться отказывается. Сообщение теряется среди сотни
строк про `readyz`, а наружу выходит только код 137, который читается как OOM.

Лечится двумя шагами. Первый — в `.wslconfig` в домашнем каталоге пользователя
Windows:

```ini
[wsl2]
kernelCommandLine = cgroup_no_v1=all
```

После `wsl --shutdown` контроллеры v1 исчезнут, но cgroup2 останется
смонтированным в `/sys/fs/cgroup/unified`, а kubelet ищет его в
`/sys/fs/cgroup`. Поэтому второй шаг — внутри дистрибутива:

```bash
umount /sys/fs/cgroup/unified && mount -t cgroup2 none /sys/fs/cgroup
```

Это не переживает перезапуск WSL — удобно положить в `/etc/wsl.conf` в секцию
`[boot]`.

Заодно выяснилось, что **k3s заметно легче kind**: control-plane занимает около
600 МБ против примерно двух гигабайт. На машине с восемью гигабайтами это
разница между «работает» и «не помещается».

## Запуск на локальном кластере

```bash
k3d cluster create monetka --agents 0 --no-lb --k3s-arg "--disable=traefik@server:0"
```

Образ надо **загрузить в кластер**: узлы не видят локальный демон Docker, и без
этого под уйдёт в `ImagePullBackOff`.

```bash
k3d image import monetka-api:latest --cluster monetka
```

```bash
kubectl apply -k k8s/base
```

```bash
kubectl -n monetka get pods -w
```

Проверить API:

```bash
kubectl -n monetka port-forward svc/monetka-api 8000:8000
```

Снести всё:

```bash
kubectl delete -k k8s/base
```

**PVC при этом останутся.** Это не ошибка, а защита от потери данных — и
причина, по которой пересозданный под видит старые данные. Удалять явно:

```bash
kubectl -n monetka delete pvc --all
```

## Что здесь стоит рассмотреть

Четыре места, ради которых этот перенос и делался.

### `depends_on` не существует

В Compose порядок задавался одной строкой. В Kubernetes его нет — и это
осознанное решение авторов: `depends_on` ждал *запуска* контейнера, а не
*готовности* сервиса, то есть гарантировал не то, что нужно.

Здесь порядок обеспечивают `initContainers` (отрабатывают до основного
контейнера) и `readinessProbe` (под не попадает в балансировку, пока не готов).
Многословнее, но честнее.

### Том приходит принадлежащим root

В Compose это решал отдельный сервис `workspace-init`. Здесь — `initContainer`
в том же поде: он часть пода и гарантированно отрабатывает до основного
контейнера, а не «примерно тогда же».

Контейнер работает под uid 999, том создаётся от root — без этого шага первое
же обращение к складу падает с `Permission denied`.

### Три пробы отвечают на три разных вопроса

`startupProbe` даёт время подняться — без неё `liveness` убивает под раньше,
чем он успел запуститься, и получается `CrashLoopBackOff` на пустом месте.
`readinessProbe` убирает из балансировки, не убивая. `livenessProbe` убивает —
поэтому проверяет **только сам процесс**, а не зависимости: проба, ходящая в
базу, превращает её недоступность в перезапуск здоровых подов.

### `requests` против `limits`

У Postgres они равны — это класс `Guaranteed`, его вытеснят последним при
нехватке памяти на ноде. У API `requests` меньше `limits` — класс `Burstable`,
дешевле, но при всплеске может быть вытеснен.

Превышение лимита памяти — это `OOMKilled` и код 137. Тот самый, с которым
падал Trino на восьмигигабайтной машине.

## Чего здесь нет и почему

**Redpanda, SeaweedFS, Trino, Iceberg REST.** Все три — StatefulSet с PVC по
той же схеме, что Postgres, плюс headless Service для брокера. Не добавлены
не из-за сложности, а из-за памяти: на локальном кластере поверх WSL с лимитом
5 ГБ они не помещаются рядом с остальным. Для учебного переноса это ничего не
отнимает — механика у них та же, что у Postgres.

**Ingress.** Для локального кластера хватает `port-forward`. В настоящем
окружении нужен контроллер (nginx, Traefik) — сам по себе объект Ingress ничего
не делает, и это частая потеря времени: создал, ничего не происходит, потому
что контроллера нет.

**Airflow.** Отдельная задача: сейчас он ходит в сокет Docker-демона, а в
кластере так нельзя. Там `KubernetesPodOperator`, который создаёт поды через
API и требует ServiceAccount с правами через RBAC. Это следующий шаг и хорошее
упражнение — ровно то, чего ждут от MLOps-инженера.

**Helm.** Для одного окружения он только добавляет слой. Здесь Kustomize,
встроенный в `kubectl`. Если окружений станет три — overlay'и ложатся поверх
этой же базы без переписывания.

## Главное ограничение, которое перенос делает видимым

Склад DuckDB — один файл с одним писателем. В Compose это было неявно, здесь
становится явным: том `ReadWriteOnce`, одна реплика, никакого масштабирования.

Попытка поднять вторую реплику даст под в `Pending` — и это честнее тихой порчи
файла.

Выход из ограничения в платформе уже заложен: Trino поверх Iceberg читает те же
данные без ограничения на одного писателя. То есть миграция на масштабируемое
хранилище наполовину сделана ещё до того, как понадобилась.
