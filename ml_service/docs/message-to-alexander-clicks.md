# Сообщение Александру: как подключить клики

Готово к отправке.

---

Саш, привет. Про подключение кликов.

**Главное: событие — это не клик, а изменение состояния.** Разница практическая.
Если слать каждое нажатие, поток забьётся навигацией («открыл Магазин»,
«вернулся», «снова открыл»), а модели и витрины считают по действиям: купил,
отложил, поставил цель, закрыл период. Навигация в аналитике пригодится потом,
и её лучше слать отдельным типом, а не мешать с экономикой.

Поэтому вешать `track()` на каждый `onPressed` не надо. Правильное место — там,
где меняется локальное состояние.

## Куда именно ставить

Одна точка на действие, рядом с записью в локальную базу:

| Экран | Действие | Событие |
|:---|:---|:---|
| Магазин | покупка подтверждена | `purchase_made` |
| Магазин | не хватило денег, покупка отклонена | `purchase_rejected` |
| Цели | цель выбрана | `goal_selected` |
| Цели | цель достигнута | `goal_reached` |
| Копилка | отложил | `savings_deposited` |
| Копилка | снял | `savings_withdrawn` |
| Доход | начислено | `income_granted` |
| План | план на период отправлен | `budget_plan_submitted` |
| Итог | период закрыт | `period_closed` |
| Советчик | подсказка показана | `hint_shown` |
| Задания | начал / завершил | `quest_started` / `quest_completed` |
| Питомец | состояние изменилось | `pet_state_changed` |

`hint_shown` важнее, чем кажется: без него нельзя измерить, помогает ли
подсказка. Он и делает возможным сравнение «модель против правила».

## Как это выглядит в коде

Не по одному вызову на кнопку, а одна обёртка, через которую проходят все
действия:

```dart
// одно место на всё приложение
await events.track(
  'purchase_made',
  payload: {
    'item_id': item.id,
    'item_category': item.isEssential ? 'essential' : 'optional',
    'price': item.price,
    'balance_before': before,
    'balance_after': after,
  },
);
```

Внутри `track()` делает три вещи, и все три обязательны:

1. **Генерирует `event_id`** — UUID, прямо в приложении. Не на сервере. Тогда
   повторная отправка после потери сети отбросится по нему, а не удвоит
   историю.
2. **Ставит `occurred_at`** — время действия, а не отправки. Не переписывать
   при отправке: иначе неделя офлайна схлопнется в одну минуту, и всё, что
   считается по времени, поедет.
3. **Пишет в локальную очередь той же транзакцией**, что и изменение
   состояния. Иначе после падения между ними одно есть, другого нет.

Отправка отдельно от записи: появилась сеть — шлём пачкой до 5000 на
`POST /v1/events:batch`, удаляем из очереди **после** ответа. Ответ приходит со
счётчиками `accepted / duplicates / rejected` и позициями отвергнутых.

## Чего в события класть нельзя

Ни имени, ни email, ни телефона, ни `user_id`. Идентификатор профиля —
псевдоним, его считает бэкенд. Событие с похожим полем не запишется: приём
вернёт 422, это требование ТЗ §3.5, и оно проверяется кодом.

Отдельно: название, которое пользователь вписал сам, не должно попадать в
идентификатор. В `item_id` идёт категория или id позиции каталога, а не
свободный текст.

## Про API на 91.210.106.86:6767

Две вещи, которые стоит поправить до демо:

**Сейчас это HTTP без TLS.** По нему ходят JWT — то есть токен доступа летит
открытым текстом, и любой на пути его прочитает. Для демо с одного ноутбука
терпимо, для публичного адреса — нет. Нужен сертификат, хотя бы Let's Encrypt.

**Android по умолчанию не пустит приложение на `http://`** начиная с API 28:
cleartext-трафик запрещён. Либо TLS, либо временное исключение в
`network_security_config.xml` — но тогда его точно нельзя забыть убрать.

## Что приложение получает обратно

`POST /v1/hint` — подсказка по снимку периода. В запросе **нет
идентификаторов**, только показатели периода, поэтому сервис не может накопить
профиль ребёнка.

Таймаут 50 мс и обязательно локальное правило на случай, если не ответили: ТЗ
§2.5.7 требует, чтобы объяснение было всегда. Медиана ответа сейчас 0.5 мс, так
что таймаут — страховка, а не рабочий режим.

Полный разбор — `ml_service/docs/integration-contract.md`.
