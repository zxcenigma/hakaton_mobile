# TLS перед API: что развернуть и почему именно так

Сейчас API отвечает по адресу `http://91.210.106.86:6767` открытым текстом.
Проверено сегодня: порт отвечает `200` на `/openapi.json`, порты 80 и 443 на
сервере открыты, 22 тоже.

Конфигурация готова и проверена локально. **Применить её на сервер я не могу —
доступа по SSH у меня нет**, и пароль просить не буду. Ниже ровно те команды,
которые нужно выполнить, и объяснение каждой.

---

## 1. Почему это не «доделаем потом»

Две причины, и вторая важнее первой.

**JWT уходит в открытом виде.** Его видит любой узел по дороге: роутер в кафе,
провайдер, кто угодно в той же публичной сети. Перехваченный токен — это вход
в аккаунт ребёнка. ТЗ §3.5 запрещает утечку детских данных прямо.

**Приложение на Android 9 и новее к этому адресу уже не достучится.** Начиная с
API 28 открытый HTTP запрещён по умолчанию. В манифесте
`mobile_app/android/app/src/main/AndroidManifest.xml` нет ни
`usesCleartextTraffic`, ни `networkSecurityConfig` — значит запрос просто не
уйдёт. В отладчике это выглядит как «сервер недоступен», и время уходит на
проверку сервера, который работает.

То есть TLS здесь — не улучшение безопасности, а условие работоспособности.

---

## 2. Почему Caddy, а не nginx с certbot

nginx + certbot — это конфиг nginx, отдельный клиент ACME, cron на продление,
пути к сертификатам в двух местах и перезагрузка nginx после обновления. Пять
мест, где можно ошибиться, и ломается это молча через три месяца, когда
сертификат истекает.

Caddy получает и продлевает сертификат сам, без cron. Конфигурация — один файл
из пятнадцати строк. Для сервиса, за которым некому следить ежедневно, это
решает главную проблему: просроченный сертификат.

## 3. Почему имя `91-210-106-86.sslip.io`, а не IP

Let's Encrypt выдаёт сертификаты на доменные имена, а не на голые IP-адреса.
`sslip.io` — публичный DNS, который резолвит такое имя обратно в тот же адрес.
Проверено:

```
91.210.106.86   91-210-106-86.sslip.io
```

Это рабочий способ получить **настоящий** сертификат, пока своего домена нет.
Самоподписанный не подошёл бы: его пришлось бы вшивать в приложение, и каждая
смена сертификата означала бы новую сборку в магазине.

Когда появится свой домен — поменять имя в `Caddyfile` и перезапустить прокси.
Больше ничего.

---

## 4. Что развернуть

Два новых файла, оба уже в репозитории. Ничего существующего не менялось:

| Файл | Что делает |
|:---|:---|
| `backend/docker/Caddyfile` | Сам прокси: TLS, заголовки, редирект со старого адреса |
| `backend/docker/docker-compose.proxy.yaml` | Контейнер Caddy на сети `hakaton_mobile_proxy` |

Сеть `hakaton_mobile_proxy` в основном `docker-compose.yaml` уже объявлена как
`external` — место под прокси было оставлено там изначально.

### Команды на сервере

```bash
cd ~/hakaton_mobile && git pull
```

Почту для уведомлений Let's Encrypt поправить в `backend/docker/Caddyfile`
(строка `email`) — на неё придёт письмо, если продление однажды сломается.

```bash
docker network create hakaton_mobile_proxy
```

Если сеть уже есть, команда скажет об этом и ничего не сломает.

```bash
docker compose -f backend/docker/docker-compose.proxy.yaml up -d
```

Первый запуск занимает до минуты: Caddy проходит проверку Let's Encrypt на
порту 80. Посмотреть, что получилось:

```bash
docker logs -f hakaton_mobile_caddy
```

Проверить снаружи:

```bash
curl -sI https://91-210-106-86.sslip.io/openapi.json
```

## 5. Обязательный шаг после: закрыть 6767

Пока порт `6767` открыт наружу, TLS ничего не защищает — старый открытый путь
продолжает работать, и приложение (или кто угодно) может ходить по нему.

В `backend/docker/docker-compose.yaml` публикация уже ограничена локальным
адресом:

```yaml
ports:
  - "127.0.0.1:6767:6767"
```

Но снаружи порт **отвечает** — значит на сервере его открывает что-то ещё:
правило firewall, проброс или другая версия файла. Проверить и закрыть:

```bash
sudo ufw status numbered
```

```bash
sudo ufw delete allow 6767
```

После этого `curl http://91.210.106.86:6767/openapi.json` должен перестать
отвечать, а `https://91-210-106-86.sslip.io/openapi.json` — отвечать.

## 6. Что поменять в приложении

**Адрес API** — на `https://91-210-106-86.sslip.io` (без порта, 443 по
умолчанию).

**Сетевую политику** — файл готов:
`ml_service/app-integration/android/network_security_config.xml`.

Положить в `mobile_app/android/app/src/main/res/xml/` и сослаться в манифесте,
в теге `<application>`:

```xml
android:networkSecurityConfig="@xml/network_security_config"
```

Политика запрещает открытый HTTP явно и разрешает пользовательские
сертификаты (Charles, mitm-прокси) **только в отладочной сборке** — блок
`debug-overrides` в релизный APK не попадает физически, его нельзя забыть
выключить перед публикацией.

## 7. Что проверено, а что нет

**Проверено локально:**

- `caddy validate` на боевом `Caddyfile` — `Valid configuration`.
- Сквозной прогон «Caddy с TLS → upstream» на внутреннем CA: `HTTP/2 200`,
  тело проходит, заголовки `Strict-Transport-Security`, `X-Content-Type-Options`,
  `X-Frame-Options`, `Referrer-Policy` на месте, заголовок `Server` не отдаётся.
- `91-210-106-86.sslip.io` резолвится в нужный адрес.
- Порты 80 и 443 на сервере открыты, значит проверка Let's Encrypt пройдёт.

**Не проверено, потому что требует доступа к серверу и к сборке приложения:**

- Само получение сертификата от Let's Encrypt. Риск низкий — всё, от чего оно
  зависит, проверено выше, — но пока это предсказание, а не факт.
- Что именно открывает порт 6767 наружу. Виден результат, не причина.
- Поведение приложения с новой политикой: Flutter-проект лежит в ветке
  `frontend`, и трогать чужую ветку я не стал.

---

## 8. Ограничение, о котором стоит знать заранее

`sslip.io` — чужой публичный домен. Он работает и им пользуются, но:

- у Let's Encrypt есть лимиты на выдачу, и они общие для всего `sslip.io`;
- если сервис однажды выключат, перестанет резолвиться имя, а вместе с ним
  отвалится и приложение.

Для хакатона и демонстрации это приемлемо. Для продукта, который пойдёт к
детям, нужен свой домен — он стоит несколько сотен рублей в год и снимает оба
пункта. Замена делается в одной строке `Caddyfile`.
