# Kubernetes для дата-инженера: курс под переход в MLOps

Курс написан под конкретного человека: ты знаешь Docker Compose, Airflow и
Spark, строил ETL под SLA и уже наступал на OOMKill и на пробы, которые ходят в
`localhost`. Поэтому здесь нет «что такое контейнер» — здесь про то, чем
Kubernetes отличается и где он кусается.

Формат: читаешь раздел, делаешь упражнение, идёшь дальше. В конце — миграция
платформы «Монетки», она же артефакт для резюме.

---

## Часть 0. Зачем это вообще

Честный ответ, с которого стоит начать: **Kubernetes не делает ничего, чего
нельзя сделать без него.** Compose запускает контейнеры, systemd их
перезапускает, nginx балансирует. Вопрос не в возможностях, а в том, кто
держит систему в нужном состоянии, когда ты спишь.

Compose — это **императив**: «запусти вот это». Упало — упало. Kubernetes —
это **декларация**: «в системе должно быть три реплики этого». Дальше работает
цикл согласования: контроллер постоянно сравнивает желаемое состояние с
фактическим и устраняет разницу. Нода умерла — поды переедут. Под убили —
создастся новый. Ты описал результат, а не шаги к нему.

Это и есть единственная идея, которую надо понять по-настоящему. Всё остальное
— детали вокруг неё.

**Для MLOps конкретно** Kubernetes нужен по трём причинам: там живут
GPU-планировщики (без него шарить карту между задачами нечем); там работают
инференс-серверы в проде (vLLM, Triton разворачивают туда); и там же строятся
Kubeflow, KServe, Ray — всё, что спрашивают в вакансиях.

## Часть 1. Модель мышления

### 1.1. Цикл согласования

Это не метафора, а буквально устройство системы.

```
  ты говоришь API-серверу: «хочу 3 реплики»
                 │
                 ▼
          etcd (желаемое состояние)
                 │
     ┌───────────┴───────────┐
     ▼                       ▼
  контроллер            фактическое
  сравнивает  ◄──────── состояние
     │
     └─► создаёт/удаляет, пока не сойдётся
```

Отсюда следствия, которые важнее самого механизма:

**Нет команды «перезапусти».** Есть «измени желаемое состояние так, чтобы
текущие поды перестали ему соответствовать». Поэтому `kubectl rollout restart`
под капотом просто меняет аннотацию в шаблоне пода.

**Нет гарантии, что под останется жив.** Он может быть вытеснен из-за нехватки
памяти, переехать при обновлении ноды, быть убит при изменении шаблона.
Приложение обязано это переживать — то есть быть идемпотентным и не хранить
состояние в себе. Для тебя это знакомо: ты уже строил идемпотентные DAG'и,
потому что перезапуск был нормой. Здесь это становится законом.

**Декларация означает, что «как есть сейчас» не важно.** Ты не чинишь систему,
ты исправляешь описание. Это меняет привычки: правка через `kubectl edit` на
проде — то же самое, что `UPDATE` без `WHERE` в понедельник утром.

### 1.2. Что в кластере из чего состоит

Минимально достаточная картина:

| Компонент | За что отвечает | Аналогия из твоего опыта |
|:---|:---|:---|
| **API-сервер** | Единственная дверь. Всё идёт через него | Координатор в Spark |
| **etcd** | Хранит желаемое состояние | Метастор Hive |
| **Scheduler** | Решает, на какой ноде запустить под | YARN ResourceManager |
| **Controller Manager** | Крутит те самые циклы согласования | Планировщик Airflow |
| **kubelet** | Агент на ноде, запускает контейнеры | NodeManager в YARN |

Если держать в голове соответствие с YARN — почти всё ложится на место.
Разница в том, что YARN планирует задачи, а Kubernetes — долгоживущие сервисы.

## Часть 2. Объекты, в порядке реальной нужды

### 2.1. Pod — и почему ты почти никогда не создаёшь его руками

Под — это один или несколько контейнеров с общим сетевым пространством и общими
томами. Внутри пода контейнеры видят друг друга по `localhost`.

**Главное: под смертен и не воскресает.** Если создать под напрямую и он
упадёт — всё, его нет. Поэтому поды создают контроллеры.

Исключение, где под руками уместен: разовая отладка.

```bash
kubectl run tmp --rm -it --image=busybox:1.36 -- sh
```

**Sidecar-паттерн.** Несколько контейнеров в поде нужны, когда они обязаны
жить и умирать вместе: основной сервис и сборщик логов, сервис и прокси. Для
ML — основной контейнер и контейнер, подтягивающий модель из реестра при
старте.

### 2.2. Deployment — для того, что можно перезапустить где угодно

Это то, чем ты будешь пользоваться в 80 % случаев. Deployment управляет
ReplicaSet, ReplicaSet — подами.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: monetka-api
spec:
  replicas: 2
  selector:
    matchLabels: { app: monetka-api }
  template:
    metadata:
      labels: { app: monetka-api }
    spec:
      containers:
        - name: api
          image: monetka-api:latest
          ports: [{ containerPort: 8000 }]
```

**Селектор обязан совпадать с метками шаблона.** Это первая ошибка новичка:
Deployment «не видит» свои поды, потому что метки разъехались. Kubernetes не
подскажет — он просто создаст поды и не будет ими управлять.

**Стратегии обновления.** `RollingUpdate` по умолчанию: поднимает новые поды,
гасит старые. `maxSurge` — сколько лишних можно поднять, `maxUnavailable` —
сколько можно погасить. Для сервиса в одной реплике `maxUnavailable: 0` даёт
обновление без простоя, но требует места под лишний под.

### 2.3. StatefulSet — для того, что нельзя

Разница с Deployment принципиальная, и дата-инженеру она ближе всех.

| | Deployment | StatefulSet |
|:---|:---|:---|
| Имена подов | случайные | предсказуемые: `pg-0`, `pg-1` |
| Порядок запуска | любой | строго по очереди |
| Хранилище | общее или никакого | у каждого пода своё, переживает пересоздание |
| Сетевое имя | только через Service | у каждого своё DNS-имя |

**Когда нужен:** базы, Kafka, ZooKeeper, всё, где под №1 не равен поду №2.
Postgres в Deployment с двумя репликами — это две базы, которые дерутся за один
том и портят данные.

Твой случай: склад DuckDB — файл с **одним писателем**. В Kubernetes это
означает StatefulSet с одной репликой и `ReadWriteOnce`-томом, а не Deployment
с двумя.

### 2.4. Job и CronJob — для конвейеров

Job выполняет под до успешного завершения. CronJob запускает Job по
расписанию.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata: { name: monetka-nightly }
spec:
  schedule: "0 3 * * *"
  concurrencyPolicy: Forbid     # не запускать второй, пока идёт первый
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: pipeline
              image: monetka-api:latest
              command: ["monetka", "demo"]
```

**`concurrencyPolicy: Forbid` обязателен для ETL.** Без него медленный прогон
догоняется следующим, и два процесса пишут в один склад. Ты это знаешь по
Airflow как `max_active_runs=1` — здесь то же самое другими словами.

**`backoffLimit` — не то же, что retries в Airflow.** Это число попыток всего
Job'а, и между ними экспоненциальная задержка, которой ты не управляешь.

### 2.5. Service — стабильный адрес для нестабильных подов

Поды получают IP и теряют его при пересоздании. Service даёт постоянное имя.

| Тип | Что делает | Когда |
|:---|:---|:---|
| `ClusterIP` | Адрес внутри кластера | По умолчанию, для внутренних связей |
| `NodePort` | Порт на каждой ноде | Отладка, локальный кластер |
| `LoadBalancer` | Внешний балансировщик облака | Прод в облаке |
| `Headless` (`clusterIP: None`) | DNS отдаёт IP каждого пода | StatefulSet, когда нужен конкретный под |

**DNS внутри кластера:** `имя-сервиса.namespace.svc.cluster.local`, и внутри
того же namespace достаточно просто `имя-сервиса`. То есть в `.env` вместо
`http://seaweedfs:9000` будет ровно то же — compose-привычка переносится.

### 2.6. Ingress — вход снаружи

Service типа LoadBalancer на каждый сервис — дорого и неудобно. Ingress — один
вход, маршрутизация по хосту и пути, и там же TLS.

Сам по себе Ingress — только описание. Работу делает контроллер (nginx,
Traefik), и его надо поставить отдельно. Частая потеря времени у новичка:
создал Ingress, ничего не происходит, потому что контроллера в кластере нет.

## Часть 3. Хранилище — самое сложное для дата-инженера

Здесь больше всего боли, и здесь же твой опыт одновременно помогает и мешает.

### 3.1. Три уровня

**PersistentVolume (PV)** — кусок хранилища, существующий в кластере.
**PersistentVolumeClaim (PVC)** — заявка пода: «хочу 10 ГБ с таким доступом».
**StorageClass** — как создавать PV автоматически, когда приходит заявка.

Поток: под ссылается на PVC → PVC подбирает или создаёт PV через StorageClass →
том монтируется.

### 3.2. Режимы доступа, и почему это главное

| Режим | Что значит | Реальность |
|:---|:---|:---|
| `ReadWriteOnce` (RWO) | Пишет одна **нода** | Почти все блочные диски: EBS, GCE PD, local-path |
| `ReadOnlyMany` | Читают многие | Редко |
| `ReadWriteMany` (RWX) | Пишут многие | Только сетевые ФС: NFS, CephFS, EFS |

**Главная ловушка:** `ReadWriteOnce` — это одна *нода*, а не один под. Два пода
на одной ноде том разделят, на разных — второй не запустится и зависнет в
`Pending`. Это объясняет 90 % «под не стартует, а событий нет».

Для твоего склада DuckDB это даже кстати: один писатель — ограничение, которое
RWO навязывает принудительно.

### 3.3. Что будет с данными при пересоздании

| Объект | Переживает удаление пода | Переживает удаление контроллера |
|:---|:---|:---|
| `emptyDir` | нет | нет |
| PVC в Deployment | да | да (PVC отдельный объект) |
| `volumeClaimTemplates` в StatefulSet | да | **да, PVC остаются после удаления StatefulSet** |

Последнее удивляет: удалил StatefulSet — PVC остались. Это защита от потери
данных, но она же приводит к «почему новый под видит старые данные».

### 3.4. Упражнение

Подними Postgres как StatefulSet с PVC, запиши строку, удали под, убедись, что
строка на месте. Потом удали StatefulSet и создай заново — строка снова
окажется там, и ты поймёшь про `volumeClaimTemplates`.

## Часть 4. Ресурсы, лимиты и OOMKill

Раздел, который ты оценишь: ты уже ловил смерть WSL из-за памяти.

### 4.1. requests и limits — разные вещи

**`requests`** — сколько гарантированно выделить. По нему **планировщик**
выбирает ноду.
**`limits`** — потолок. По нему **ядро** убивает или тормозит.

```yaml
resources:
  requests: { memory: "512Mi", cpu: "250m" }
  limits:   { memory: "1Gi",   cpu: "1" }
```

`250m` — это 0.25 ядра. CPU — ресурс сжимаемый: превышение лимита приводит к
троттлингу. Память — нет: превышение приводит к **OOMKill**, под умирает с
кодом 137.

Код 137 ты уже видел — Trino падал с ним на 8-гигабайтной машине.

### 4.2. Классы QoS, и почему их стоит знать

Kubernetes сам назначает классы, и от них зависит, кого убьют первым при
нехватке памяти на ноде:

| Класс | Условие | Убивают |
|:---|:---|:---|
| `Guaranteed` | requests == limits для всех контейнеров | последним |
| `Burstable` | requests < limits | вторыми |
| `BestEffort` | ничего не указано | **первыми** |

Отсюда правило: **критичным сервисам ставь requests равными limits.** Это
стоит дороже, но их не вытеснят ради чужого всплеска.

### 4.3. Как читать смерть пода

```bash
kubectl describe pod <имя> | grep -A5 "Last State"
```

`Reason: OOMKilled, Exit Code: 137` — не хватило памяти, поднимай лимит.
`Exit Code: 1` — упало само приложение, смотри логи.
`Reason: Error` без кода — часто проба здоровья, см. следующую часть.

## Часть 5. Пробы — и та самая ошибка с localhost

### 5.1. Три пробы, три смысла

| Проба | Вопрос | Что будет при провале |
|:---|:---|:---|
| `startupProbe` | «Запустился?» | Остальные пробы ждут её |
| `readinessProbe` | «Готов принимать трафик?» | Под убирают из Service, но не убивают |
| `livenessProbe` | «Жив?» | Под **убивают** и создают заново |

**Самая частая и самая дорогая ошибка — liveness, которая проверяет не то.**
Если liveness ходит в базу, а база прилегла, Kubernetes начнёт убивать
совершенно здоровые поды приложения. Получается каскад: база медленная →
приложение перезапускается → нагрузка растёт → база ещё медленнее.

Правило: **liveness проверяет только сам процесс. Зависимости — readiness.**

### 5.2. Про localhost

Ты это уже проходил: проба ходила в `localhost`, он резолвился и в `::1`, а
сервис слушал только IPv4 — и здоровый сервис объявлялся больным. В k8s то же
самое, только теперь это приводит к перезапуску, а не к красной колонке.

В `httpGet` поле `host` по умолчанию — IP пода, и это обычно правильно. Но если
пишешь `exec` с `curl`, указывай `127.0.0.1` явно.

### 5.3. `startupProbe` для медленных стартов

Trino поднимается полторы минуты. Без `startupProbe` liveness начнёт убивать
его на тридцатой секунде, и под уйдёт в бесконечный цикл перезапусков с
`CrashLoopBackOff`. Правильно:

```yaml
startupProbe:
  httpGet: { path: /v1/info, port: 8080 }
  failureThreshold: 30
  periodSeconds: 10        # итого до 5 минут на запуск
livenessProbe:
  httpGet: { path: /v1/info, port: 8080 }
  periodSeconds: 15
```

## Часть 6. Конфигурация и секреты

**ConfigMap** — неконфиденциальные настройки. **Secret** — конфиденциальные.

Важное, что часто понимают неправильно: **Secret не шифрует.** Это base64,
то есть кодирование, а не защита. Без включённого шифрования etcd секреты
лежат в нём открытым текстом. Настоящие варианты — внешние хранилища
(Vault, облачные Secret Manager) через CSI-драйвер или External Secrets.

```yaml
envFrom:
  - configMapRef: { name: monetka-config }
  - secretRef:    { name: monetka-secrets }
```

**Подводный камень:** под **не перезапускается** при изменении ConfigMap, если
значения проброшены через `env`. Смонтированные как файлы — обновляются, но с
задержкой до минуты. Самый надёжный способ — класть хеш конфига в аннотацию
шаблона пода: изменился конфиг — изменился шаблон — прошёл rolling update.

## Часть 7. Наблюдаемость

Твой опыт с Prometheus и Grafana переносится почти целиком, меняется только
способ находить цели.

**`ServiceMonitor`** (из Prometheus Operator) описывает, какие Service
скрейпить. Вместо ручного списка в `prometheus.yml` — метки.

**Логи.** `kubectl logs` показывает текущий контейнер, `--previous` — тот, что
умер (именно там причина CrashLoopBackOff). В проде нужен сборщик: Loki,
ELK, Vector — под удаляется вместе с логами.

**Метрики, на которые смотреть сразу:** `kube_pod_container_status_restarts_total`
(рестарты — первый признак беды), `container_memory_working_set_bytes` против
лимита, `kube_pod_status_phase{phase="Pending"}` (поды, которым не хватило
места).

## Часть 8. Что нужно именно для MLOps

Это то, ради чего всё затевалось.

### 8.1. GPU

Карта выдаётся как ресурс:

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

Для этого на нодах нужен `nvidia-device-plugin`, а в контейнерном рантайме —
`nvidia-container-toolkit`.

**Главное ограничение:** по умолчанию GPU **не делится**. Запросил — получил
карту целиком, даже если тебе нужно 10 % памяти. Отсюда три способа шаринга,
которые и спрашивают на собеседованиях:

| Способ | Как работает | Изоляция | Когда |
|:---|:---|:---|:---|
| **Time-slicing** | Задачи по очереди на одной карте | Нет: процессы видят общую память | Разработка, инференс мелких моделей |
| **MPS** | Один контекст CUDA на всех | Слабая, падение одного роняет остальных | Много мелких задач от доверенных владельцев |
| **MIG** | Карта делится аппаратно на изолированные части | **Полная**, аппаратная | Прод, multi-tenant. Только A100/H100 |

Ответ на собеседовании звучит так: time-slicing — дёшево и без изоляции, MPS —
быстро и без защиты от падений, MIG — единственный с настоящей изоляцией, но
требует подходящего железа и фиксированной нарезки.

### 8.2. Инференс LLM

**vLLM** — самый частый выбор под LLM. Ключевая идея — PagedAttention:
KV-кэш хранится страницами, как виртуальная память, вместо непрерывного блока.
Это даёт в разы больше одновременных запросов на той же карте.

**Triton Inference Server** — универсальный: несколько фреймворков,
динамическое батчирование, ансамбли моделей.

**TGI** — от Hugging Face, проще развернуть, меньше гибкости.

При разворачивании в k8s главное: модель **не класть в образ** (он станет
десятками гигабайт) — тянуть из хранилища в `initContainer` на общий том.

### 8.3. Квантование — то, что просят «оптимизировать инференс»

Смысл: веса в меньшей разрядности занимают меньше памяти и считаются быстрее,
ценой точности.

| Метод | Суть |
|:---|:---|
| **GPTQ** | Послойная квантизация с коррекцией ошибки, обычно 4 бита |
| **AWQ** | Бережёт веса, важные по активациям; часто лучше качество при той же разрядности |
| **GGUF** | Формат под CPU-инференс (llama.cpp) |

**Как мерить** — ты уже умеешь: таблица до и после. Пропускная способность,
p50/p95 задержки, занятая память и качество на наборе задач. Ровно то, что ты
делал для ONNX, где получилось 527 мс против 0.35 мс.

### 8.4. Операторы и платформы поверх

**Kubeflow** — зонтик: пайплайны, тюнинг гиперпараметров, сервинг. Тяжёлый.
**KServe** — только инференс, зато умеет автомасштабирование до нуля.
**Ray** — распределённые вычисления, часто для обучения и батч-инференса.
**Volcano / Kueue** — планировщики пакетных задач с очередями и честным
распределением, то, чего не умеет стандартный scheduler.

Начинать стоит не с Kubeflow. Сначала просто разверни что-нибудь руками —
понимание придёт быстрее.

## Часть 9. Инструменты, без которых больно

**Helm** — шаблонизатор манифестов. Нужен, когда одно и то же разворачивается в
dev/stage/prod с разными значениями. Минус: `values.yaml` сложного чарта
читается хуже, чем сами манифесты.

**Kustomize** — встроен в `kubectl` (`kubectl apply -k`). Не шаблоны, а
наложение патчей на базу. Для twoй задачи — трёх окружений одного стека —
обычно достаточно и понятнее Helm.

**k9s** — текстовый интерфейс к кластеру. Экономит часы на отладке.

**ArgoCD / Flux** — GitOps: кластер подтягивает состояние из git сам. То, что
в вакансии названо «методология GitOps». Идея простая и сильная: git —
единственный источник правды, ручные изменения откатываются автоматически.

## Часть 10. Что реально ломается у всех

Собрано по частоте, а не по важности.

**`CrashLoopBackOff`.** Контейнер падает, k8s перезапускает с нарастающей
задержкой. Смотреть `kubectl logs --previous`. Чаще всего: нет переменной
окружения, нет файла конфига, liveness убивает слишком рано.

**`ImagePullBackOff`.** Образ не скачивается. Приватный реестр без
`imagePullSecrets`; опечатка в теге; в kind/minikube образ есть локально, но
не загружен в кластер (`kind load docker-image`).

**`Pending` без событий.** Нет ноды, удовлетворяющей requests. Либо ресурсов
нет, либо PVC не привязался, либо `nodeSelector` не совпал.
`kubectl describe pod` → раздел Events.

**Под не видит сервис.** Метки селектора не совпадают. `kubectl get endpoints
<service>` — если пусто, Service не нашёл поды.

**Данные пропали после обновления.** Был `emptyDir` вместо PVC.

**Приложение не читает новый конфиг.** ConfigMap через `env` не обновляется без
перезапуска пода.

**Всё работает в dev и падает в проде.** В dev не было лимитов, в проде есть.

## Часть 12. Миграция «Монетки»: что с чем переносится

Это главное упражнение, потому что переносишь то, что понимаешь целиком.

| Сейчас в Compose | В Kubernetes | Почему так |
|:---|:---|:---|
| `api` | **Deployment** + Service | Без состояния, можно масштабировать |
| `postgres` | **StatefulSet** + PVC | База, под №1 не равен поду №2 |
| `seaweedfs` | **StatefulSet** + PVC | Хранит данные на диске |
| `redpanda` | **StatefulSet** + PVC, Headless Service | Брокеру нужны стабильные имена |
| `trino` | **Deployment** + `startupProbe` | Без состояния, но стартует полторы минуты |
| `iceberg-rest` | **Deployment** | Без состояния |
| `ingestor` | **Deployment**, 1 реплика | Консьюмер; больше одной — конфликт за склад |
| `*-init` | **Job** с `initContainers` у зависимых | Одноразовые, должны завершиться до старта |
| `airflow` | **Deployment** + RBAC | Запускает Job'ы — нужны права в API |
| `.env` | ConfigMap + Secret | Секреты отдельно от настроек |
| `./data` | PVC `ReadWriteOnce` | **Один писатель** — ограничение DuckDB |
| `depends_on` | `initContainers` + readiness | В k8s нет depends_on, порядок — через готовность |

Три решения, которые придётся принять осознанно:

**Склад DuckDB.** Один файл, один писатель. В Compose это терпимо, в k8s —
архитектурное ограничение: том RWO, одна реплика, никакого масштабирования.
Это ровно то место, где в настоящем проде DuckDB меняют на Trino поверх Iceberg
— а у тебя он уже есть, то есть миграция уже наполовину сделана.

**Airflow, запускающий контейнеры.** Сейчас DockerOperator ходит в сокет
демона. В k8s так нельзя — там `KubernetesPodOperator`, который создаёт поды
через API и требует ServiceAccount с правами. Это не лишняя работа, а именно
то, чего ждут от MLOps-инженера.

**`depends_on` не существует.** Порядок обеспечивается тем, что зависимый под
не стартует, пока `initContainer` не дождётся готовности зависимости. Выглядит
многословнее, но честнее: compose ждал запуска контейнера, а не готовности
сервиса.

## Часть 13. Что отвечать на собеседовании

Вопросы, которые задают почти всегда, и короткие верные ответы.

**«Чем Deployment отличается от StatefulSet?»** Стабильные имена, порядок
запуска и персональное хранилище у каждого пода. Нужен базам и брокерам.

**«Что произойдёт, если под превысит лимит памяти?»** OOMKill, код 137. CPU
сжимаем — троттлится; память нет — убивают.

**«Зачем readiness, если есть liveness?»** Readiness убирает из балансировки,
liveness убивает. Если liveness проверяет зависимости, падение базы вызовет
каскад перезапусков здоровых подов.

**«Как обеспечить порядок запуска?»** Через initContainers и readiness.
`depends_on` в k8s нет, и это правильно: ждать надо готовности, а не старта.

**«Безопасен ли Secret?»** Нет, это base64. Без шифрования etcd он лежит
открытым текстом. Настоящая защита — внешнее хранилище через CSI.

**«Как поделить GPU между задачами?»** Time-slicing, MPS или MIG. Настоящая
изоляция только у MIG, и только на A100/H100.

**«Под в Pending, что делать?»** `describe` и смотреть Events: нехватка
ресурсов, непривязанный PVC или несовпадение nodeSelector.
