## Полный вариант

Саш, привет. Коротко по ML-части — что сделано и зачем она вообще в проекте.

**Сначала главное: ТЗ машинное обучение не требует.** П. 2.7.5 прямо выносит
ИИ, ML, большие данные и облако за границы обязательного решения. Основной
игровой цикл обязан работать офлайн, на устройстве, без сервера (п. 3.1.5).
Поэтому ML у нас не вместо механики, а поверх неё — и включается только там,
где это можно обосновать.

П. 3.2 разрешает применять ML при трёх условиях: объяснить, какую задачу
решаем, какие данные обрабатываем и как контролируем корректность. Мы
выполнили все три буквально:

1. **Задача.** Три модели, у каждой карточка с задачей, границами и запретами.
   Первая выбирает, *какое объяснение* показать ребёнку в «Советнике». Вторая
   ранжирует задания под текущий уровень. Третья помечает аномальные периоды
   для методиста.
2. **Данные.** Только синтетическая телеметрия. Персональные данные детей не
   собираются (п. 3.5) — это не обещание в документации, а проверка в коде:
   контракты событий отвергают любое поле, похожее на персональные данные, и
   сборка падает. API отвергает такой запрос с 422, проверено на живом сервисе.
3. **Контроль корректности.** Гейты качества: модель не выкладывается, если не
   прошла порог. Сравнение с правилами на случайно назначенных группах.
   Проверка паритета после конвертации в ONNX. Мониторинг дрейфа.

**Что ML сознательно НЕ делает:** не трогает игровую экономику. Не меняет
цены, доход и правила. Иначе игра перестанет быть предсказуемой для ребёнка, и
мы не объясним жюри, почему у двух детей разные цены. Это записано отдельным
решением в репозитории.

**И самое важное для защиты:** если модель недоступна или отвечает дольше
50 мс — показывается правило. Fallback обязателен, потому что п. 2.5.7 требует,
чтобы объяснение было всегда, а не когда сервис ответил. То есть ML улучшает
приложение, но приложение без него работает полностью.

**Статус.** Сервис лежит в `ml_service/` на ветке `dev_ml`. Работает на
синтетических данных — генератор моделирует четыре архетипа поведения детей,
которые учатся по ходу игры. Когда появятся реальные события, меняется один
источник, весь конвейер остаётся. Поднятый стек проверен вживую: хранилище
пишется и читается, API отвечает, подсказки приходят.

Если будет минута — посмотри `ml_service/docs/backend-integration-review.md`,
там разбор связки мобилка/бэк/ML и что в каком порядке достраивать.

## Короткий вариант

Саш, привет. По ML коротко.

ТЗ его не требует — п. 2.7.5 выносит ИИ и ML за обязательный минимум, а
основной цикл обязан работать офлайн. Поэтому мы применяем ML только там, где
п. 3.2 разрешает: объяснили задачу, данные и контроль корректности.

Три модели: какое объяснение показать в «Советнике», какие задания
предложить, какие периоды пометить методисту. Персональные данные детей не
собираются — это проверяется кодом, а не обещано в документации. Экономику игры
ML не трогает вообще.

Ключевое для защиты: если модель недоступна или медленнее 50 мс — показывается
правило. Приложение полностью работает без ML, ML только улучшает.

Сервис в `ml_service/` на ветке `dev_ml`, работает на синтетике, стек поднят и
проверен. Разбор связки с бэком — в `ml_service/docs/backend-integration-review.md`.
